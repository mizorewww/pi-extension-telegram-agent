# 设计与哲学

这一章讲这个 bot 为什么长成现在这样。它不是客服，也不是“一个会聊天的 API”，而是群里的一个成员：有性格，会沉默，被叫到一定回应，需要时能动手干活。下面每条原则都对应着代码里真实的取舍。

## 1. 什么时候说话由代码决定，说什么由模型决定

是否调用模型完全由本地确定性代码判断：@、回复、叫名字必定触发；普通消息按概率最多交给一个 bot，忙碌或冷却中就跳过，不改投给别人。bot 之间看得到彼此，但默认不互相触发。

被人直接点名会生成一条持久的**回复义务**：直到 bot 真的在群里发了言才算结清。provider 报错、daemon 重启、压缩，义务都不会丢；被点名却沉默时，最多补问一次。反过来，Telegram 发送结果不确定时**绝不重发**——宁可偶尔漏一句，也不刷屏。

## 2. 三个世界，各管各的

1. **Telegram 群**只是传输层，不负责恢复历史。
2. **SQLite** 是事实来源：从运行起看到的每条消息、编辑、媒体描述、后台结果都以只追加的事件记录下来。
3. **Pi / LLM** 只在需要思考时看到有界的精简上下文。

模型的上下文是从数据库投影出来的，不是从 Telegram 现拉的。所以重启后能接着聊，翻旧消息靠 `tg_messages` 去库里查，而不是把整个群塞进 prompt。

## 3. 极简：一套设计，不留兼容层

- 配置只有一个来源：`telegram.config.ts` + Pi 自己的设置 + `.env` 里的 secret。
- 改设计就一步到位，不保留旧字段、旧模式和迁移阶梯。只有一个生产部署，旧库直接报错，比维护迁移更不容易出错。
- 删代码优先于加抽象；防御代码只防真实可能发生的分支。

## 4. Pi 原生优先

能交给 Pi 的都交给 Pi：会话与持久化、重试、压缩钩子、steer 队列、模型目录与认证、图片缩放、codemode 沙箱（后台 job 也直接复用 Pi 的 `CodemodeSandbox`）、TUI 组件。

自己写的只有 Pi 确实没有、或者 Pi 的版本不适合“缓存敏感、多 bot、带沙箱”的场景的部分：

| 自己写的 | 为什么不用 Pi 的 |
|---|---|
| 摘要器 | Pi 的摘要器用固定英文模板、不能带图、会保留 thinking；保留推测曾让一次误读变成“事实”被一代代继承 |
| provider 看门狗 | Pi 的 `timeoutMs` 只对支持它的 SDK 生效，不是整条流的截止时间 |
| session 裁剪 | Pi 没有公开的裁剪 API |
| 后台任务的 RPC 帧 | Pi 的 `RpcClient` 写死了 `node` 子进程，跑不了 `docker run` |
| daemon ↔ TUI 的 IPC | Pi 的 RPC 一进程一会话；这里一个 daemon 要同时服务多个 bot |

不采用的 Pi 功能也有原因：运行中切换工具集、`context_edit`、会话内换模型都会改写已发送的前缀，破坏缓存；skills 和 prompt template 会往 system prompt 里加字节，所以关掉。

## 5. 不花冤枉钱

能用确定性代码解决的不花 token；每个功能先估 cache 命中率和每轮新增 token。

1. **不该调用模型就不调用。** 路由、翻历史、看用量、群内管理命令都不经过模型。
2. **严格前缀。** system prompt、persona、sticker 目录、工具说明逐字节不变；新内容只追加，每个请求都是下一个请求的严格前缀。实测同一轮内后续请求平均只 miss 约 780 token，而一旦前缀被改写，即使间隔不到 30 秒也要多付上万 token。
3. **每轮只发需要的。** 完整历史在本地库里；每轮只发有上限的新消息（默认 12,000 token），被点名的优先；接近阈值时用便宜的摘要模型压缩。
4. **媒体只处理一次。** 同一张图无论多少 bot 看到，只描述一次并复用；视频只抽 1–3 帧。平时模型只看文字描述，真想细看时自己用 `view_image` 打开原图。
5. **工具结果有界。** 搜索最多 5 条短结果，网页一次读一页；脚本只把筛选后的结果交给模型。
6. **发言即结束。** 直接调用 `send` 成功后本轮立刻结束，不多花一次请求去“确认”。

部分 provider 的目录单价为 0（订阅制），这时显示的费用不代表账单，以 provider 账户为准。

## 6. 给能力和例子，不给规矩

- bot 只被告知它真正拥有的工具；没开的功能它会如实说做不到。
- persona 只写人格和回应风格；每个工具的用法写在工具说明下面，配足可以直接照抄的例子。这些例子都在真实工具上跑过。
- 限制只放在真有风险的地方。为了“让 bot 克制一点”而加的条数上限、窗口限制，实测只会让它拒绝合理的请求，已经全部删掉；剩下的上限只防失控循环，不写进提示词。
- 鼓励探索：bot 知道自己的源码仓库，被问到“你是怎么工作的”时会去读代码再回答。

## 7. 安全靠机制，不靠提示词

提示词可以被绕过，边界必须是机械的：

- **codemode 脚本**跑在 Pi 的 QuickJS VM 里，没有网络、文件系统和宿主 API，只能调用开放给脚本的工具。
- **工作区**是每 bot 一个的 rootless Docker 容器，跑在独立系统用户下：不挂载宿主目录、去掉全部 capability、只读根文件系统，只有一个 `/work` 卷；每周一清空，管理员随时可以 `/box reset`。容器里没有任何凭据。
- **search** 只访问公网 HTTP(S)，内网、回环、云元数据地址一律拒绝。
- **改状态的群内命令**只有人类管理员能用，命令消息永远不进模型上下文。

`test/` 里只剩守这些边界和缓存不变量的几个测试。

## 8. 先想清楚再写

不搞 TDD。先把设计想清楚——它属于哪一层、会不会改写缓存前缀、Pi 是不是已经有了——再写代码。正确性靠类型检查、在服务器上真实运行，以及对真实工具跑一遍提示词例子的 e2e，而不是堆积锁定实现细节的单测。

## 刻意不做的事

- 不用 Telegram Rich Message 发言：没更新的客户端看不到，Bot API 也不会报错。
- 不自动打开群里的链接：只有 bot 自己决定用 `search` 时才读。
- 一份部署只对应一个群：多群用独立的 clone，不加第二层命名空间。
- 不在发送结果未知时重发。
